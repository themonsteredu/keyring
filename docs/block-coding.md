# 블록코딩으로 실제 키링 움직이기

키링 스튜디오의 **블록 코딩** 화면에서는 Google Blockly 블록을 연결해 프로그램을 만듭니다. 브라우저의 미리 실행뿐 아니라 ESP32에 저장한 프로그램도 실제 OLED를 바꿉니다. 프로그램은 기기 내부에서 해석해 실행하므로, 저장 후에는 스마트폰 연결 없이도 동작합니다.

## 처음 만드는 표정 순서

1. **블록 코딩** 화면을 엽니다.
2. **키링 시작할 때** 블록 아래에 다음 순서로 블록을 연결합니다.

   ```text
   키링 시작할 때
   말랑눈으로 바꾸기
   행복한 표정
   1초 기다리기
   사랑하는 표정
   1초 기다리기
   ```

3. **미리 실행**을 누르고 표정이 순서대로 바뀌는지 확인합니다.
4. **계속 반복**을 켜면 마지막 블록 뒤에 첫 블록부터 다시 실행합니다.
5. 내 키링 Wi-Fi에 연결한 기기 화면에서 **키링에 저장**을 누르고 실제 OLED를 봅니다.

표정 블록만 연달아 놓으면 명령이 빠르게 실행되어 마지막 표정만 보일 수 있습니다. 중간 표정을 관찰하려면 기다리기 블록을 넣습니다. 시작 블록은 하나만 두고 모든 명령을 그 아래에 연결합니다. 떨어진 블록이 있거나 시작 블록이 여러 개이면 실행·내보내기를 진행할 수 없으므로 연결을 확인하세요.

## 블록이 하는 일

| 블록 | 실행 결과 | 예시 |
| --- | --- | --- |
| 시작 | 실행을 시작할 위치 | 아래에 순서대로 연결 |
| 눈 모양 | 선택한 눈 모양으로 바꾸고 표정 화면 표시 | 말랑눈, 초롱눈, 웃음눈, 콩알눈, 네모눈 |
| 감정 | 선택한 표정으로 바꾸고 표정 화면 표시 | 행복, 신남, 졸림, 슬픔, 화남, 사랑 |
| 기다리기 | 다음 명령까지 정해진 시간 기다리기 | 1초; 허용 범위 0.1~30초 |
| 날씨 보여주기 | 저장된 날씨 화면으로 바꾸기 | 다음에 5초 기다리기를 두어 관찰 |
| 정해진 횟수 반복 | 안쪽 블록들을 1~20번 반복 | 행복→기다리기→사랑→기다리기를 3번 |
| 날씨 조건 | 조건에 맞으면 첫 가지, 아니면 다른 가지 실행 | 비이면 슬픔, 아니면 행복 |

시작은 프로그램 진입점이며 저장 파일에서는 루트 프로그램으로 표현됩니다. 별도의 센서나 물리 버튼을 가정하지 않습니다. 전체 반복 옵션은 프로그램 전체를 계속 실행하는 기능이고, 횟수 반복 블록은 안쪽 명령을 지정한 횟수만 실행하는 기능입니다.

## 날씨 조건을 올바르게 읽기

조건은 블록에 도달한 시점에 **저장된 `current.code`**를 읽습니다. 조건이 바뀔 때 자동으로 깨우는 이벤트가 아닙니다. 반복할 때마다 조건을 다시 검사하려면 조건 블록을 반복 안에 둡니다.

- `sun`: 맑음 계열 WMO 코드 0·1
- `cloud`: 구름·안개 계열 2·3·45·48
- `rain`: 비·이슬비·소나기·뇌우 계열
- `snow`: 눈 계열 71·73·75·77·85·86

**샘플·오래된 예보·시계 미확인 상태도 저장된 코드가 있으면 조건에 사용합니다.** 저장된 날씨가 없으면 조건은 거짓이어서 아니면 가지를 실행합니다. 따라서 조건 분기의 결과를 현재 바깥 날씨의 확인 결과라고 설명하지 않습니다. 웹과 날씨 화면의 출처·업데이트 시각·유효 상태를 함께 읽으세요. 날씨 조건과 날씨 보여주기 블록은 인터넷에서 새 예보를 다운로드하지 않습니다.

수업에서는 명시적인 샘플을 사용해 분기를 연습할 수 있습니다. 이때 샘플 표시를 그대로 유지하고, 실제 날씨를 확인하려면 새 예보 파일을 가져옵니다. 시간 처리의 자세한 기준은 [날씨 안내](weather.md)에 있습니다.

## 온라인 화면에서 실제 기기로 옮기기

[온라인 키링 스튜디오](https://keyring-swart.vercel.app)에는 실제 ESP32 API가 없습니다. 온라인 미리 실행은 브라우저 안에서 실행되는 것이며 기기에 저장되었다는 뜻이 아닙니다.

1. 인터넷이 되는 상태에서 프로그램을 만들고 미리 실행합니다.
2. **코드 파일 저장**을 눌러 `keyring-program.json`을 내려받습니다. 날씨 JSON과는 다른 파일입니다.
3. 스마트폰을 내 `Keyring-XXXXXX` Wi-Fi로 바꿉니다.
4. `http://192.168.4.1`의 **블록 코딩** 화면에서 **코드 불러오기**를 눌러 프로그램 파일을 가져옵니다.
5. **키링에 저장**을 누릅니다. 저장·실행 결과를 확인하고 실제 OLED의 순서를 봅니다.

**코드 불러오기**는 편집기에 블록을 불러오는 기능입니다. 아직 기기를 바꾸지 않습니다. **키링에 저장**을 누르면 실행을 켠 프로그램이 기기에 저장되고 바로 실행합니다. 파일을 가져오기 전 내 키링에 연결했는지 확인하세요. 온라인 HTTPS 페이지가 ESP32의 HTTP 주소로 직접 저장하도록 우회하지 않습니다.

## 저장·정지·재부팅

| 행동 | 결과 |
| --- | --- |
| 미리 실행 | 브라우저 미리보기만 실행, 실제 기기 저장과 별개 |
| 키링에 저장 | 실행을 켠 프로그램을 기기에 저장한 뒤 처음부터 실행 |
| 멈추기 | 미리보기 정지. 연결된 기기에 저장 프로그램이 있으면 기기도 정지하고 수동 화면으로 복귀하며 자동 실행을 끔 |
| 꾸미기에서 직접 적용 | 프로그램을 정지하고 선택한 수동 설정 저장 |
| 전원 재연결 | 실행을 켜 둔 프로그램은 처음부터 실행; 정지한 프로그램은 자동 실행하지 않음 |
| 반복하지 않는 프로그램 완료 | 이번 부팅에는 마지막 출력 유지; 자동 실행이 켜져 있으면 다음 부팅에 다시 실행 |
| 처음부터 | 편집기의 초기 예제로 돌아가기. 기기 저장 내용은 그대로 |
| 키링 전체 초기화 | 수동 설정을 기본값으로 복원하고 저장 날씨·프로그램 삭제 |

실행 중 어느 블록까지 갔는지는 저장하지 않습니다. 재부팅 후 중간 지점이 아니라 첫 명령부터 시작합니다. 프로그램이 눈 모양·표정을 바꾸는 것은 매번 NVS에 설정을 쓰는 일이 아닙니다. 프로그램과 수동 설정을 구분해서 저장합니다.

**새 눈·입 표정과 한글 날씨는 새 펌웨어에 들어 있습니다.** Vercel 화면만 바꾸어서는 실제 OLED 그림이 바뀌지 않습니다. 이 버전의 통합 펌웨어를 먼저 업로드합니다. 프로그램 API가 없는 이전 펌웨어 역시 업로드가 필요합니다. [업로드 안내](hardware-and-upload.md)를 따르며 GPIO4·GPIO5 배선과 코어 3.3.7은 그대로 유지합니다.

## 도전 과제

- 두 가지 감정을 1초씩 보여 주는 순서를 만들고 3번 반복해 보세요.
- 기다리기를 0.5초와 2초로 바꾸고 느낌이 어떻게 달라지는지 설명해 보세요.
- 비이면 슬픔, 아니면 행복을 고르고 각 가지 뒤에 기다리기를 넣어 보세요.
- 표정을 3초 보여 준 뒤 날씨를 5초 보여 주는 순서를 만들어 보세요.
- 프로그램을 정지하거나 꾸미기에서 직접 적용한 뒤 재부팅 결과를 예상해 보세요.

교사는 순서와 기다리기를 기본 활동으로, 반복과 조건을 도전 활동으로 나눌 수 있습니다. 정답 그림을 복제하는 것보다 학생이 순서와 결과를 설명하는지 확인합니다.

## 개발자를 위한 프로그램 파일

화면의 눈 모양은 우유팩 케이스 안 OLED의 눈·입 디자인을 고르는 기능입니다. 저장 호환성을 위해 프로그램의 `character` 명령과 기존 값 `rabbit`, `cat`, `bear`, `turtle`, `monster`는 유지합니다. UI에서는 각각 말랑눈, 초롱눈, 웃음눈, 콩알눈, 네모눈으로 표시하며 동물 몸을 그리지 않습니다.

프로그램은 JavaScript 소스 대신 제한된 명령 트리(AST)로 저장합니다. 스키마 1의 루트 필드는 `schema`, `enabled`, `loop`, `blocks`이며 모두 필요합니다. 명령 종류를 나타내는 키는 **`type`**입니다. 다음은 실제 구조에 맞는 예제입니다.

```json
{
  "schema": 1,
  "enabled": true,
  "loop": true,
  "blocks": [
    {"type": "character", "value": "rabbit"},
    {"type": "emotion", "value": "happy"},
    {"type": "wait", "ms": 1000},
    {
      "type": "repeat",
      "count": 3,
      "blocks": [
        {"type": "emotion", "value": "love"},
        {"type": "wait", "ms": 1000},
        {"type": "emotion", "value": "happy"},
        {"type": "wait", "ms": 1000}
      ]
    },
    {"type": "weather"},
    {"type": "wait", "ms": 5000}
  ]
}
```

조건 명령의 형식은 다음과 같습니다.

```json
{
  "type": "ifWeather",
  "kind": "rain",
  "then": [{"type": "emotion", "value": "sad"}],
  "else": [{"type": "emotion", "value": "happy"}]
}
```

루트 `blocks`에는 한 개 이상의 명령이 필요합니다. 반복·조건의 안쪽 배열은 비어 있을 수 있습니다. 전체 명령은 중첩된 모든 가지를 합쳐 최대 64개, 중첩 깊이는 루트 1부터 최대 4입니다. 기다리기는 정수 밀리초 100~30,000, 횟수 반복은 정수 1~20입니다. 허용하지 않는 종류·값·필드가 포함된 파일은 거부합니다. 내보낸 프로그램 JSON에 임의의 Blockly 작업 공간 메타데이터나 실행 코드를 추가하지 않습니다.

펌웨어는 할당과 실행량을 제한한 네이티브 해석기로 실행합니다. 기다리는 동안 HTTP·Wi-Fi와 OLED 처리도 계속 진행하고, 기다리기가 없는 반복도 한 번에 무한 실행하지 않도록 처리합니다. Google Blockly는 로컬 웹 자산으로 제공하며 [Apache License 2.0](https://github.com/google/blockly/blob/develop/LICENSE)을 따릅니다. 해당 라이선스 고지를 배포 자산과 함께 유지합니다.

소프트웨어 테스트와 타깃 컴파일 결과는 [실행 기록](verification.md)에서 버전을 구분해 확인합니다. 실제 보드에서 저장·자동 실행·정지·재부팅을 확인하는 것은 [교사용 실물 확인표](teacher-guide.md)의 별도 항목입니다.
